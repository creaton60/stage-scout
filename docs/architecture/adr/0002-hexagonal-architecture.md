# ADR-0002. 헥사고날 아키텍처를 채택한다

- 상태: 채택
- 일자: 2026-09-05

## 맥락

이 시스템의 외부 의존이 유난히 많고 유난히 불확실하다.

- 지도: Naver Map. 부지 경계를 안 주면 공공데이터로 보강해야 한다.
- 사진 분석: 6주 안에 온프레미스 모델 ↔ 외부 비전 API 를 오갈 가능성이 높다.
- 기상: 출처 미정.
- 저장: 초기엔 인메모리로 빠르게, 이후 PostGIS.

반면 도메인 규칙(역광 판정, 수용 인원 환산, 시야각 기준)은 안정적이며,
이 규칙들이야말로 제품의 가치다.

## 결정

포트-어댑터(헥사고날) 구조를 쓴다.

```
domain → 아무것도 모름
application → domain 만 앎, 외부는 Protocol 로만 만남
adapter → 바깥 기술. 교체 대상
config → 유일한 조립 지점
```

의존 규칙은 문서가 아니라 `tests/unit/domain/test_dependency_rule.py` 로 강제한다.
ruff 의 `flake8-tidy-imports.banned-api` 로도 이중 방어한다.

## 결과

**좋은 점**
- 지도·비전 어댑터 없이 도메인·유스케이스를 테스트할 수 있다 → S3~S5 가 외부 API 진척에 안 막힌다.
- S1 은 인메모리 저장소로 수직 슬라이스를 끝내고, S2 에서 PostGIS 로 갈아끼운다.

**치르는 비용**
- 파일 수와 간접 계층이 는다. 6주짜리 프로젝트에 과하다는 지적이 가능하다.
- 그래도 채택하는 이유: 위 외부 의존 4개 중 최소 2개는 6주 안에 실제로 바뀔 것으로 본다.

## 대안

- **레이어드(Controller-Service-Repository)** — 익숙하지만 서비스가 외부 SDK 를 직접 안다.
  사진 분석 모델을 갈아끼울 때 유스케이스까지 흔들린다.
- **트랜잭션 스크립트** — 더 빠르게 시작하지만 배치 최적화 규칙이 라우터에 눌어붙는다.
