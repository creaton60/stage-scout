# Sprint 3 — 공연 일자 기준 적합도 평가

| | |
|---|---|
| 주차 | W3 |
| 담당 요구사항 | FR-3 (일자별 적합도 평가) |
| 브랜치 | `sprint-3-suitability` |
| 선행 | S2 (후보지 데이터) |

## 목표

**"그날 그 장소가 왜 좋은가/나쁜가"에 답한다.**
같은 공원도 5월 오후 2시와 10월 오후 5시가 완전히 다르다 — 태양이 어디 있는지,
비가 올 확률이 얼마인지, 2,000명이 들어가는지. 이 스프린트는 그 판단을 숫자와
**사람이 읽을 수 있는 문장**으로 만든다.

## 끝나면 보여줄 수 있는 것

후보지 5곳이 점수 순으로 정렬되고, 각 점수 옆에
"오후 5시 이후 관객이 서향 태양을 정면으로 봅니다 (역광 노출 42%)" 같은 근거가 붙는다.

## 설계 사항

- [ ] **평가 축과 가중치 확정** — 역광 20% / 기상 25% / 접근성 20% / 수용력 25% / 평탄도 10%
      가중치는 도메인 정책이므로 `domain/service/suitability.py` 에 두고 ADR 로 근거를 남긴다
- [ ] **정규화 규칙 설계** — 축마다 단위가 다르다(비율, mm, m, 명). 0~1 로 어떻게 환산할지
- [ ] **역광 판정 모델** — 관객 시선 = 무대 정면의 역방향.
      태양 방위와의 사잇각 45° 이내를 역광으로 보고, 고도 15° 이하에서 가중
- [ ] **근거 문장 생성 규칙** (NFR-4) — 모든 점수에 최소 1개. 템플릿과 임계값 정의
- [ ] **기상 예보 한계 정책** — 10일 초과 일자는 평년값으로 대체하고 **그 사실을 근거 문장에 명시**
- [ ] **태양 계산 방식** — 외부 API 대신 `astral` 로 자체 계산 (오프라인 테스트 가능)

## 개발 사항

- [ ] `SolarAdapter` 구현 (`SolarPort`) — 일출·일몰·시간대별 고도·방위 (FR-3.1)
- [ ] `WeatherAdapter` 구현 (`WeatherPort`) — 강수확률·강수량·기온·풍속·풍향 (FR-3.3)
- [ ] `domain/service/glare.py` 구현 — `glare_ratio()` 역광 노출 비율 (FR-3.2)
- [ ] 수용력 평가 — 예상 관객 수 대비 가용 면적 (FR-3.4)
- [ ] 접근성 평가 — S2 의 `AccessProfile` 을 점수로 환산
- [ ] `domain/service/suitability.py` 가중 합산 완성
- [ ] 근거 문장 생성기 — 축별 `CriterionScore.reason` 채우기
- [ ] `EvaluateVenuesService` 구현 (FR-3.5)
- [ ] 라우터 `GET /events/{id}/venues:ranked`
- [ ] 웹: 후보지 순위 목록 + 점수 분해(breakdown) 표시

## 검증할 사항

- [ ] 알려진 날짜·좌표의 일출/일몰이 실제와 ±2분 이내 (예: 2026-06-21 서울)
- [ ] 정서향 무대 + 하지 오후 6시 → 역광 판정이 나온다 (경계 케이스 고정 테스트)
- [ ] 정북향 무대 → 한국 위도에서 역광이 나오지 않는다
- [ ] 가중치 합이 1.0 이고, 축 하나를 빼도 `total` 이 0~1 범위를 유지한다
- [ ] **모든 `CriterionScore` 에 빈 문자열이 아닌 `reason` 이 있다** (NFR-4 자동 검사)
- [ ] 예보 범위(10일) 밖 일자에서 평년값 대체 사실이 근거 문장에 나타난다
- [ ] 기상 API 장애 시 해당 축만 제외하고 나머지로 순위가 나온다 (전체 실패 금지)
- [ ] 후보지 5곳 평가가 3초 이내 (NFR-1)
- [ ] 동일 입력 → 동일 순위 (NFR-3)

- **FR-3.4** 수용력 평가
