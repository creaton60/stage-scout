# 로드맵 — 6주 / 6 스프린트

## 제품 한 줄 정의

> 공연 기획자가 **공연 일자**를 입력하면, 지도에서 후보지를 찾아 그날 조건에 맞게 순위를 매기고,
> 현장에서 찍어온 **사진**을 근거로 무대와 관객석을 어디에 놓을지 배치도를 만들어 준다.

## 왜 이 순서인가

가치 사슬이 한 방향으로 흐르고, 뒤 단계는 앞 단계의 산출물 없이는 검증이 불가능하다.

```
공연 요구사항  →  지도 후보지  →  일자별 적합도  →  현장 사진 분석  →  배치 최적화  →  배치도 출력
    S1             S2              S3                S4               S5             S6
   (등록)        (수집)          (선정)            (실측)           (설계)         (전달)
```

- **S1~S2** 가 밀리면 전부 밀린다 → 지도 API 연동 리스크를 1주차에 PoC 로 먼저 깬다.
- **S4(사진→지도 좌표 정합)** 가 기술 난도 최상 → S1 에 스파이크를 미리 배치해 실패를 조기에 발견한다.
- **S5** 는 S3(환경 점수) + S4(지형 제약)를 모두 입력으로 받는다 → 두 산출물의 인터페이스를 S1 의 포트 정의에서 못박는다.

## 스프린트 요약

스프린트별 상세 계획은 각 스프린트 브랜치의 `docs/planning/sprint-N.md` 와 해당 PR 본문에 있다.

| # | 주차 | 목표 | 끝나면 보여줄 수 있는 것 | 브랜치 |
|---|---|---|---|---|
| S1 | W1 | 기반 구축 · 도메인 모델링 · 리스크 스파이크 | 공연 등록 API 가 도는 수직 슬라이스 | `sprint-1-foundation` |
| S2 | W2 | Naver Map 연동 · 후보지 수집 | 지도에서 후보지 찾아 목록으로 보기 | `sprint-2-map-data` |
| S3 | W3 | 공연 일자 기준 적합도 평가 | "그날 이 장소가 몇 점인지" 근거와 함께 | `sprint-3-suitability` |
| S4 | W4 | 현장 사진 → 지형/장애물 분석 | 사진 올리면 가용 영역 폴리곤이 지도에 | `sprint-4-site-survey` |
| S5 | W5 | 무대·관객 배치 최적화 | 배치안 3개 자동 생성 | `sprint-5-layout` |
| S6 | W6 | 배치도 시각화 · 출력 · 안정화 | PDF 배치도 다운로드, 데모 | `sprint-6-visualization` |

## 스프린트 운영

- 기간: 1주 (월 시작 ~ 금 종료)
- 월 오전: 계획 / 금 오후: 리뷰 + 회고
- 각 스프린트는 **동작하는 수직 슬라이스**로 끝난다. "이번 주는 설계만" 은 없다.
- 완료 기준은 [definition-of-done.md](definition-of-done.md) 를 따른다.

## 전체 리스크 (스프린트 무관하게 계속 본다)

| 리스크 | 영향 | 대응 | 언제 판단 |
|---|---|---|---|
| Naver Map 이 부지 경계 폴리곤을 제공하지 않음 | 면적·배치 계산 불가 | 공공데이터 연속지적도 병행, 수동 폴리곤 입력 UI 백업 | S1 스파이크 |
| 사진 → 지도 좌표 정합 정확도 부족 | 배치안 신뢰도 붕괴 | 지면 평면 가정 + 사용자 보정 UI 로 폴백 | S1 스파이크, S4 확정 |
| EXIF 방위 정보 없는 사진이 다수 | 정합 자체가 불가 | 촬영 가이드 제공 + 수동 방위 지정 UI | S4 |
| 지도 API 호출량/비용 한도 | 운영 비용 급증 | 좌표 기준 캐시, 정적 지도 재사용 | S2 |
| 개인정보(사진 속 행인, 위치정보) | 법적 리스크 | 온프레미스 분석 우선, 얼굴 마스킹 | S4 |
